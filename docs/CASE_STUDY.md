# LLM Tool Calling Lab development case study

LLM Tool Calling Lab is an experimental local chatbot for developers exploring how language models can choose and use numerical ML tools. Its first implementation combines four task families, a shared model catalog, validated execution, and recorded evidence. Live development checks demonstrate the tool workflow and follow-up comparisons. The completed frozen benchmark found no completion benefit from the added planning instructions: generic chat passed 33/48 supported held-out conversations and structured orchestration passed 31/48. These results do not establish improved reasoning or production reliability.

## The engineering problem

A conversational interface must translate a question into a supported task, choose an eligible method, and explain its output. A plausible response alone cannot establish that a model ran, that the data split was valid, or that its results support the explanation. The prototype makes those boundaries inspectable and gives developers a concrete place to replace a specialist model.

The implementation uses a local Qwen model through Ollama, a Streamlit interface, and eight scikit-learn methods across regression, binary classification, anomaly detection, and clustering. Questions and follow-ups share a bounded episode. The executor controls preprocessing, data partitions, model fitting, and timeouts; the chatbot chooses among permitted operations.

## A tool interface failure and its correction

An earlier development run exposed a mismatch between the nested tool schema and the arguments generated by the chatbot. Calls omitted the required task family, invented settings such as a validation split, or supplied unsupported grouping fields. Validation rejected these calls, and some conversations exhausted their repair or response allowance. Those failures remain in the earlier smoke records.

The native tool interface was flattened to make the method, family, dataset, features, and optional target or scoring batch explicit. Data splits and estimator settings remained fixed in the executor. The next four-family check returned successful structured responses for every initial question and comparison follow-up. This sequence supports the interface change as a useful development correction; it is not a controlled estimate of its effect.

## What the working demonstration shows

Each of the four development episodes fitted two methods and compared recorded results. In the regression example, the follow-up changed the selected method from Random Forest to Ridge after comparing validation error. Classification, anomaly detection, and clustering also completed their candidate comparisons. The anomaly conversation used its single repair allowance.

The extension tutorial separately replaced Ridge with ElasticNet through the catalog and estimator factory. Both methods produced fitted artifacts on the same synthetic dataset and partition fingerprints. This demonstrates a working replacement path, rather than an unexercised adapter template. The tutorial is excluded from the benchmark catalog. See [the adapter guide](ADAPTERS.md) for the interface and reproduction steps.

Final installed-wheel verification passed 102 automated checks covering data validation, model execution, conversation budgets, evaluation integrity, and the interface. Tests include forced timeouts, malformed adapter outputs, separation of training and test data, and evidence values rendered directly from saved results.

## Evidence and interpretation have different checks

Public model results contain validation evidence or fresh-batch rankings. Test metrics and synthetic ground-truth labels stay outside the chatbot's tools. The interface renders stored metrics and validated anomaly row IDs; failed calls remain in the transcript and consume their allowance.

The demonstrations also expose an unresolved limitation: successful execution does not guarantee careful prose. The regression response used unsupported significance language and said no further action was needed. Those statements are not endorsed by this case study. Qualitative evaluation assesses the explanation as well as the artifact through explicitly identified, unblinded AI reviews of both delivered turns. Each review records its rubric version, checks, and rationale. A later correction does not erase an earlier unsupported claim. These assessments are not independent human review, and no human-user study or improvement in human decision-making is claimed.

## Evaluation status and reproducibility

The frozen campaign compares a generic tool-calling chatbot with structured orchestration under the same model, tools, and budgets, alongside fixed specialist references. It preserves unsuccessful and interrupted episodes. All 168 required records are complete with no pending reviews. The held-out completion comparison was 33/48 versus 31/48; anomaly conversations passed only 5/24. The [results](../RESULTS.md) separate task-specific model scores, conversation quality, challenge failures and resource use.

The initial campaign, `.lab/campaign-v0.1`, encountered a runner startup defect: an absolute session path was compared with a relative campaign path. That failure occurred before any chatbot inference. Its records, manifest, and exact source archive remain preserved separately. The runner path was corrected, and the replacement campaign, `.lab/campaign-v0.1-r2`, was frozen with fresh synthetic data using seed offset `100000`. The correction did not change the chatbot prompts, model selection, or specialist behavior using held-out outcomes. The failed launch and replacement results must not be pooled.

The local evidence sources are `.lab/smoke-four-v3/results.json`, `.lab/tutorial/comparison.json`, the preserved earlier `.lab/smoke-four/` and `.lab/smoke-four-v2/` records, and the two separate campaign directories. These local working artifacts are ignored by Git; public claims should accompany the corresponding reviewed release evidence. Synthetic evidence exports preserve failures and review provenance, identify evaluator-only truth, and distinguish completed records from missing records. Both artifact audits completed without integrity findings across all 168 records. The [experimental release assets](https://github.com/Dolvido/llm-tool-calling-lab/releases/tag/v0.1.0) publish the preserved development attempts, frozen campaign evidence and source snapshots. The later installed-wheel tutorial conversation successfully selected ElasticNet after a Random Forest comparison, while again exposing unsupported significance language in its first answer. The [project README](../README.md) provides setup and evaluation commands.

## Engineering decision

**Proposed choice for Luke's review:** keep the common specialist interface, validated executor and inspectable evidence records. This experiment does not justify claiming that the extra planning prompt improves conversation completion. A focused next experiment could test an explicit artifact-backed anomaly comparison against the frozen workflow on fresh cases. It would need a separate version and evaluation; no improvement is presented as already implemented or measured in v0.1.

For inspection, follow [the claim-to-artifact evidence map](../RESULTS.md#inspect-the-evidence) to repository reports and the release archive. The `c122_generic_1` record shows why an executable result can fail completion: two anomaly methods fitted, but the follow-up repeated the first ranking instead of delivering the requested comparison. The recorded unblinded AI reviewer failed `relevant_followup`. This supports targeting delivered answers, while leaving the cause and remedy unconfirmed. The [implemented controls](../EVALUATION.md#implemented-controls-and-limits-of-the-comparison) explain fixed-seed repeats, reference fit-count asymmetry, execution order and the replacement's data/wording change.
